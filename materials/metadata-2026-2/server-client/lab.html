학생 실습실: 내 홈페이지, 서버 DB, 우리 반 아카이브

시연에서는 교수님이 서버에 파일을 올렸습니다. 이번에는 여러분이 직접 합니다. 서버 계정이나 프로그램 없이, 브라우저로 수업 서버의 학생 실습실에 들어가 세 가지를 해 봅니다. A 내 홈페이지를 서버에 올리고, B 서버 데이터베이스에 SQL로 묻고, C 사진과 소리와 영상을 아카이브에 넣어 보존합니다. 자료는 모두 (사)어린이도서연구회 권장도서 목록과 이어집니다.

들어가기 서버 안 내 자리 A 내 홈페이지 B SQL 실습실 C 우리 반 아카이브 보기 파일 다 했는지 보기 확인 문제

들어가기

준비물 노트북을 권합니다(B의 SQL은 자판으로 쓰는 것이 편합니다). 폰도 됩니다. 크롬, 엣지, 사파리 가운데 아무것이나 씁니다. 설치할 것은 없습니다.
학생 실습실 주소
http://1.201.120.29:8080/lab/

폰 카메라로 QR을 찍거나 이 주소를 누르세요.

  1. 브라우저 주소창에 http://1.201.120.29:8080/lab/을 넣습니다. 아래 QR을 폰 카메라로 찍거나, 시연 첫 화면의 학생 실습실 칸을 눌러도 됩니다.
  2. 수업 코드를 넣습니다. 칠판(화면)에 있는 것으로, 우리 반만 들어오게 하는 열쇠입니다.
  3. 아이디를 정합니다. 영문 소문자로 시작하고 영문 소문자와 숫자로 3~12자입니다(예: jhpark, reader07). 이 아이디가 내 홈페이지 주소가 되므로 학번이나 전화번호처럼 나를 드러내는 것은 피합니다.
  4. 비밀번호는 숫자 네 자리입니다. 은행이나 폰 잠금에 쓰는 번호는 쓰지 마세요. 이 서버는 http(자물쇠 없음)라서 연습용 번호만 씁니다. 잊으면 교수님이 초기화해 줍니다.
  5. 처음 들어올 때만 이름을 적습니다. 다음부터는 수업 코드, 아이디, 비밀번호만 넣으면 됩니다.

A, 약 30분

내 홈페이지: 내가 올린 파일을 서버가 건넨다

실습실의 A 내 홈페이지는 서버 안 내 폴더를 보여 주는 창입니다. 여기서 파일을 만들고, 고치고, 올리면 /u/아이디/ 주소로 누구나 볼 수 있습니다. 시연에서 교수님이 FileZilla로 한 일을 여러분이 브라우저로 합니다. 화면의 할 일 일곱 개는 서버의 방문 기록을 보고 저절로 완료로 바뀝니다.

  1. 내 주소를 열어 보기: [내 주소]를 눌러 새 탭에서 엽니다. 서버가 내 폴더의 index.html을 보내 줍니다.
  2. index.html 고쳐 저장하기: 표에서 [고치기]를 누르고 글을 바꿔 [서버에 저장]합니다. 열어 둔 탭은 그대로입니다. 새로고침해야 바뀝니다.
  3. 책 소개 페이지 만들기: 권장도서를 몇 권 골라 books.html을 만듭니다. 같은 내용이 books.json으로도 생깁니다. 사람이 보는 HTML과 프로그램이 읽는 JSON을 나란히 열어 봅니다.
  4. 내 컴퓨터의 파일 올리기: 사진이나 CSV를 올리고 주소로 엽니다. 파일 이름은 영문으로 짓습니다.
  5. 폰으로 열어 보기: 화면의 QR을 폰 카메라로 찍습니다. 방문 기록에 폰이 찍힙니다.
  6. 없는 주소를 열어 404 보기: /u/아이디/nothing.html처럼 없는 파일을 엽니다. 내 폴더에 404.html을 만들면 그 화면이 대신 나옵니다.
  7. 하위 폴더 안의 파일 열기: [새 폴더]를 만들고 그 안에 파일을 넣어 /u/아이디/폴더/파일로 엽니다. 폴더 구조가 곧 주소 구조입니다.
확인할 것화면 아래 방문 기록은 웹 서버가 남기는 접속 기록(로그)입니다. 언제, 어떤 경로를, 어떤 상태 번호(200, 404, 301)로, 몇 바이트 보냈는지가 남습니다. 응답 머리(헤더)에서는 서버가 파일 내용 앞에 붙여 보내는 Content-Type을 봅니다. 브라우저는 확장자가 아니라 이 값을 보고 HTML로 그릴지, 그림으로 보일지, 내려받을지 정합니다. PHP 파일을 올려도 실행되지 않고 글자로 보이는 것도 확인해 보세요(보안을 위해 학생 폴더에서는 막아 두었습니다).
B, 약 40분

SQL 실습실: 서버 DB에 묻고, 함께 쓰고, 내 DB를 고친다

3강의 브라우저 SQL 실습실은 DB가 내 브라우저 안에 있었습니다. 이번에는 DB가 서버 안에 있습니다. 여러분은 SQL 글자만 보내고, 서버가 실행한 결과만 돌려받습니다. 쓰는 곳은 넷이고, 곳마다 할 수 있는 일이 다릅니다. 문제를 풀면 서버가 정답 SQL의 결과와 견주어 바로 채점합니다. 쓰기 칸에서 Ctrl+Enter를 누르면 실행합니다.

곳DB할 수 있는 일배우는 것
B1 목록 DB에 묻기 (10문제)catalog.db의 book 2,175권읽기(SELECT)만WHERE, LIKE, GROUP BY, 그리고 쪽수 칸에 숫자 아닌 값이 섞이고 펴낸해에 2010-2016 같은 값이 든 ‘더러운 데이터’
B2 지은이 칸 나누기 (8문제)같은 DB의 person, credit, role읽기만‘정은주 글 | 해랑 그림’처럼 뭉친 칸을 사람과 역할로 나눈 정규화, MARC 역할 부호(aut, ill, trl), 이름 찾기와 사람 찾기의 차이

확인할 것B1에서 DELETE FROM book을 실행해 보세요. 서버가 실행하지 않고 거절합니다. 같은 SQL도 누가, 어느 DB에 보내느냐에 따라 서버가 허락하거나 거절합니다. 이것이 권한입니다. B2의 이현 문제(지은이 칸에서 ‘이현’으로 찾은 책과 이름이 정확히 ‘이현’인 사람의 책 수)는 두 수가 왜 다른지 꼭 설명해 보세요. 권위 제어가 왜 필요한지 보여 줍니다.
C, 약 50분

우리 반 아카이브: 사진, 소리, 영상을 받아 보존한다

디지털 아카이브는 파일을 ‘저장’만 하지 않습니다. 받은 파일이 보낸 것과 같은지 확인하고, 무엇인지 알아보고, 사본을 두고, 보기 쉬운 이용본을 만들고, 그 모든 일을 기록합니다. 실습실의 C 우리 반 아카이브가 이 일을 서버에서 합니다. 기계가 할 수 있는 일은 서버가, 사람만 알 수 있는 일(제목, 설명, 권리)은 여러분이 합니다.

  1. 보기 파일 받기: 아카이브 화면 오른쪽 ‘보기 파일 묶음’에서 파일을 내 컴퓨터로 받습니다. 아래 보기 파일 표에서 무엇을 볼지 미리 읽습니다.
  2. 올리기: 파일을 끌어다 놓습니다. 올리기 전에 내 컴퓨터가 파일의 SHA-256 체크섬(파일 지문)을 잽니다. 서버도 받은 파일을 다시 잽니다. 두 값이 같으면 오는 길에 한 비트도 바뀌지 않았다는 뜻입니다(전송 고정성).
  3. 보존 기록 읽기: 자료 화면 아래 ‘보존 기록’에 받음, 체크섬 계산, 전송 고정성 확인, 형식 식별, 사본 만들기, 기술 메타데이터 추출, 이용본 만들기가 차례로 남습니다. PREMIS의 사건(event)과 같은 생각입니다.
  4. 기술 메타데이터 보기: 서버가 exiftool과 ffprobe로 파일 속을 읽어 너비, 높이, 길이, 코덱, 카메라, 촬영 때, 위치를 뽑습니다. 여러분이 적지 않았는데도 파일 안에 이미 들어 있던 정보입니다.
  5. 더블린 코어 달기: 제목, 만든이, 날짜, 주제어, 설명, 권리를 적습니다. 관계 칸에서는 이 자료와 이어지는 권장도서를 고릅니다. 유형, 형식, 식별자는 서버가 채웁니다. 목록 화면의 ‘메타데이터 6/6’이 다 단 표시입니다.
  6. 고정성 검사와 되살리기: [고정성 검사]로 원본과 사본을 다시 잽니다. [비트 하나 바꾸기]를 누르면 원본의 비트 하나가 바뀝니다(손상 연습). 다시 검사하면 원본은 ‘불일치’, 사본은 ‘일치’가 나옵니다. [사본으로 되살리기]로 고친 뒤 다시 검사합니다.
  7. 내보내기: 더블린 코어 XML(oai_dc), JSON, 그리고 BagIt 꾸러미(zip)를 받아 엽니다. BagIt 안의 manifest-sha256.txt에 원본의 체크섬이 적혀 있습니다. 다른 기관으로 자료를 넘길 때 받는 쪽이 이 값으로 다시 확인합니다.
  8. 내가 찍은 것 넣기: 도서관 서가 사진, 내 목소리로 녹음한 책 소개(30초), 열람실 20초 영상을 하나씩 넣고 메타데이터를 답니다. 다른 사람의 얼굴이나 목소리가 들어가면 먼저 동의를 받습니다.

  • B: B1~B4에서 푼 문제 수(모두 29문제).
  • C: 넣은 자료 수와, 그 가운데 메타데이터 여섯 칸(제목, 만든이, 날짜, 주제어, 설명, 권리)을 다 단 자료 수. 사진, 소리, 영상을 하나씩은 넣어 보세요. 한 사람이 20건까지, 파일 하나는 100MB까지입니다.
학기가 끝나면 실습 서버와 학생 자료는 학기가 끝나면 지웁니다. 남기고 싶은 홈페이지 파일은 내 컴퓨터로 받아 두고, 아카이브 자료는 BagIt으로 내보내 두세요.

확인 문제

1. A에서 index.html을 저장했는데 열어 둔 탭은 그대로였습니다. 왜일까요?

서버는 파일이 바뀌었다고 먼저 알리지 않습니다. 브라우저가 다시 요청(새로고침)해야 새 파일을 받습니다. 시연 1단계와 같은 이유입니다.

2. B1에서는 안 되던 DELETE가 B4에서는 됩니다. 같은 서버, 같은 SQL인데 무엇이 다른가요?

B1은 모두가 함께 읽는 목록 DB라 서버가 읽기만 허락하고, B4는 나만 쓰는 복사본이라 모두 허락합니다. 서버는 SQL을 실행하기 전에 누가, 어느 DB에, 무엇을 하려는지 보고 허락할지 정합니다. 실제 도서관 시스템에서도 이용자는 목록을 찾기만 하고, 목록 사서만 고칠 수 있는 것과 같습니다.

3. cover-scan.jpg는 확장자가 jpg인데 서버는 PNG라고 했습니다. 어느 쪽을 믿어야 하나요?

파일 속입니다. 확장자는 사람이 붙인 이름표라 언제든 잘못 붙을 수 있습니다. 서버는 파일 앞부분의 서명(PNG는 89 50 4E 47)을 읽어 형식을 알아냅니다. 디지털 보존에서 형식 식별을 따로 하는 까닭입니다. 실제 아카이브에서는 DROID나 Siegfried 같은 도구가 PRONOM 형식 목록과 견주어 이 일을 합니다.

4. broken-photo.jpg는 체크섬이 ‘일치’인데 그림이 깨졌습니다. 체크섬이 틀린 것인가요?

아닙니다. 체크섬은 ‘보낸 것과 받은 것이 같은가’만 알려 줍니다. 처음부터 깨진 파일을 보냈다면 깨진 그대로 같게 받습니다. 그래서 아카이브는 고정성 확인과 별도로 형식 검증과 이용본 만들기로 파일을 실제로 쓸 수 있는지 봅니다.

5. 손상 연습에서 원본이 망가졌는데 어떻게 되살릴 수 있었나요? 사본까지 망가졌다면요?

받을 때 만든 사본의 체크섬이 처음 값과 같았기 때문에, 그 사본으로 원본을 덮었습니다. 사본까지 망가지면 되살릴 수 없습니다. 그래서 실제 아카이브는 사본을 여러 곳(다른 디스크, 다른 건물, 다른 지역)에 두고 정기적으로 고정성 검사를 합니다(LOCKSS, ‘많은 사본이 자료를 지킨다’).

6. 사진의 촬영 때와 위치는 내가 적지 않았는데 어디서 왔나요? 더블린 코어의 날짜와는 무엇이 다른가요?

카메라나 폰이 찍는 순간 파일 안(EXIF)에 적어 둔 기술 메타데이터입니다. 기계가 만들고 기계가 읽습니다. 더블린 코어의 날짜는 사람이 이 자료를 설명하려고 정해 적는 기술(記述) 메타데이터라, 예를 들어 옛 사진을 스캔한 자료라면 스캔한 날이 아니라 사진을 찍은 해를 적을 수 있습니다.

출처와 만든 방법

책 목록은 (사)어린이도서연구회 ‘추천 목록’의 서지 사항(소개글 제외)입니다. 지은이 칸을 사람과 역할로 나눈 표(person, credit, role)는 이 실습을 위해 프로그램으로 나눈 것이며, 나누기 어려운 18건은 역할을 ‘(확인 필요)’로 두었습니다. 실습실은 가비아 클라우드의 우분투 서버에서 PHP 내장 웹 서버, SQLite, ffmpeg, ExifTool로 돌아갑니다. 실습실 프로그램은 class-lab.zip의 lib, www/lab, setup 폴더에 있습니다. 보기 파일은 수업용으로 만든 것입니다.
